## MVP ROADMAP

### Этап 5: Реализация Share Extension

**Статус: завершён**

- Все требования MVP реализованы.
- Лимит текста: 5000 символов, блокировка на UI и в менеджере.
- Таймауты: 15 с на запрос, 30 с общий лимит.
- Логирование всех действий через LogManagerSharedNDJSON (App Group).
- Покрытие unit, UI, E2E тестами (≥80%).
- В CI/CD реализована автоматическая проверка размера расширения (Archive + size report, fail при >20 MB).

**Вопросы к stakeholder:**
1. Требуется ли кастомная иконка и уникальный дизайн для Share Extension (например, собственная иконка, цветовая схема и стили), либо достаточно использовать стандартные системные ресурсы и палитру основного приложения? -> Да
2. Какие типы входных данных, кроме обычного текста, планируется поддерживать в расширении: изображения, ссылки (URL), документы (PDF, DOCX) или другие форматы? -> Пока только текст
3. Необходимо ли обеспечить корректное отображение Share Extension в светлой и тёмной темах системы (dark/light mode), или достаточно полагаться на настройки темы основного приложения? -> Да
4. Существуют ли дополнительные требования или ограничения к используемой App Group (например, несколько групп, особое именование, права доступа, вместимость контейнера)? -> Нет
5. Какой максимальный размер или длину текста (в символах или токенах) следует проверять на UI-стороне и блокировать кнопку обработки, чтобы не превышать ограничения OpenAI API (например, 12000 символов или 8192 токена)? -> 5000 символов
6. Нужно ли отображать в интерфейсе предварительный просмотр (preview) выбранного пользователем текста для подтверждения перед обработкой, или достаточно лишь показывать название операции и кнопку «Обработать»? -> Не нужно даже такого. Обработка должна происходить сразу после выбора операции.

**Последовательность действий для самостоятельной реализации:**
1. Создай таргет ShareExtension, подключи CraftifyShared.
2. Настрой entitlements: App Groups, Keychain Access.
3. Реализуй `ShareExtensionManager`: чтение inventory и API‑ключа.
4. Создай `ExtensionView` с UIHostingController.
5. Отобрази кнопки операций и кнопку «Отмена».
6. Проверь наличие текста и вызови Alert при его отсутствии.
7. Реализуй токенизацию текста и блокировку кнопки.
8. При выборе операции вызови `ProcessingManager.start()`.
9. Покажи Overlay прогресса с расчётом процента.
10. Обработай таймауты: 15 с на запрос, 30 с общий.
11. При успехе скопируй результат в UIPasteboard и покажи тост.
12. Обработай ошибки (401, 429, 500 и др.) с Alert.
13. Логи всех действий через LogManagerShared.
14. Напиши UI‑тесты для success/error/timeout.
15. Проверь размер extension (Archive + size report).

**Definition Of Done:**
- Размер Share Extension ≤ 20 MB.
- UI‑тесты для всех сценариев проходят.
- Нет багов при demo‑показе stakeholder.

**Прогресс по этапу 5:**
- Внедрены ClipboardManager, ProcessingManager, соответствующие протоколы и stub-реализации для тестов.
- UI Share Extension реализует блокировку кнопок при превышении лимита текста, отображает предупреждения и обрабатывает ошибки копирования.
- Все менеджеры внедряются через протоколы (DI-friendly).
- Удалены placeholder-файлы, добавлены новые исходники и тесты.
- Обновлена документация и структура файлов.

### Этап 6: Интеграция с OpenAI API

**Вопросы к stakeholder:**
1. Какие языковые модели OpenAI (например, gpt-3.5-turbo, gpt-4, gpt-4o-mini и пр.) вы хотели бы поддержать в первой версии Share Extension? Нужно ли предусмотреть возможность переключения между моделями? -> Пока достаточно gpt-4o-mini
2. Требуется ли настраиваемая переопределяемость параметров запроса (temperature, max_tokens, top_p и др.) через интерфейс приложения, или все параметры будут фиксированы на уровне кода? -> Параметры будут фиксированы на уровне кода.
3. Какой максимально допустимый размер prompt (в символах или токенах) необходимо установить на клиенте для предотвращения ошибок API или превышения лимитов? -> 8192 токена
4. Следует ли сохранять в логах полный текст prompt (включая пользовательский ввод), или достаточно хранить только метаданные и ключевые параметры без пользовательских данных? -> Да
5. Нужно ли реализовать механизм автоматического переключения (fallback) на другую модель при сбое или недоступности основной (например, при ошибке 429 или медленном ответе), или в случае ошибки достаточно показывать сообщение об ошибке? -> Нет
6. Подтвердите стратегию повторных попыток при сетевых ошибках или ответе 429: количество попыток и интервалы (например, 3 попытки с экспоненциальным backoff: 1, 2, 5 секунд)? -> Повтор через 1, 2, 5 секунд

**Последовательность действий для самостоятельной реализации:**
1. Реализуй класс `LLMAPIClient` с URLSession (ephemeral).
2. Настрой `timeoutIntervalForRequest = 15 с`.
3. Добавь retry‑механизм (экспоненциальный backoff).
4. Создай `RequestBuilder` для сборки JSON‑тела.
5. Подставь promptTemplate и параметры в тело запроса.
6. Убедись, что заголовки Authorization и Content-Type корректны.
7. Реализуй `ResponseParser`: парсинг JSON, обработка ошибок.
8. Напиши unit‑тесты с OHHTTPStubs для ошибок 400,401,429,500.
9. Напиши интеграционный тест против mock‑сервера.
10. Инструментируй сбор статистики времени отклика.
11. Логи запросов и статуса через LogManagerShared.
12. Проверь токенизацию текста (min/max токены).
13. Добавь поддержку отмены через `Task.cancel()`.
14. Обнови документацию в `docs/openai_integration.md`.
15. Проведи нагрузочное тестирование и code review.

**Definition Of Done:**
- Unit‑ и интеграционные тесты проходят.
- Время ответа в ≥ 80% случаев соответствует требованиям.
- Документация актуальна.
